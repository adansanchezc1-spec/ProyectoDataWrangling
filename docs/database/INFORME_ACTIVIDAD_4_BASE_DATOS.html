2. Descripción Corregida de la Problemática

2.1 El Problema Inmobiliario en Bogotá D.C.

El mercado inmobiliario en Bogotá D.C. genera grandes volúmenes de información distribuida en portales comerciales abiertos (MetroCuadrado, FincaRaíz, Ciencuadras) y plataformas institucionales (Catastro Distrital, IDECA, Datos Abiertos Bogotá). Dichas fuentes emiten conjuntos de datos no estructurados o semiestructurados en formatos heterogéneos (CSV, Excel XLSX, JSON) que adolecen de severas patologías de calidad de datos:

  • Inconsistencias Semánticas y Tipológicas: Precios registrados con texto ("$ 380 millones"), tamaños de área construida con medidas diversas o valores negativos, e información faltante en atributos esenciales.
  • Valores Fuera del Dominio Normativo: Inclusión de estratos socioeconómicos inválidos (como estrato 0, 8 o 9), cuando la zonificación distrital de Bogotá contempla estrictamente los valores enteros del 1 al 6.
  • Desalineación Espacial y Territorial: Propiedades ubicadas en municipios conurbados de Cundinamarca (Chía, Soacha, Mosquera) catalogadas como pertenecientes a Bogotá, o direcciones no estandarizadas sin georreferenciación.
  • Duplicación y Redundancia Masiva: Ofertas simultáneas de un mismo inmueble físico con ligeras discrepancias tipográficas en la dirección, lo que sesga gravemente la estimación de precios y los modelos de valoración masiva.

2.2 Arquitectura en Capas y Flujo de Calidad BPMN 2.0

Para garantizar datos certificados para modelos analíticos y de Machine Learning, el sistema implementa una arquitectura en capas fundamentada en DAMA-DMBOK v2 y gobernada por un proceso BPMN 2.0 con 4 compuertas lógicas (Gateways XOR):

  • Capa Staging Inmutable (stg_inmuebles_raw): Almacena los registros exactamente como provienen de la fuente en columnas de tipo TEXT, garantizando el principio de Inmutabilidad de Origen (ISO 8000) para trazabilidad y auditoría forense.
  • Capa Working Normalizada (wrk_inmuebles_cleaned): Registra únicamente las filas que superan las compuertas de validación de estructura, tipo y dominio.
  • Capa Analítica de Features (fct_features_analiticas): Feature Store desacoplado que calcula ratios numéricos y métricas de amenidades respetando el principio SOLID de Responsabilidad Única.
  • Capa Master Data Management - Golden Record (mdm_inmuebles_maestros & dim_entorno_urbano): Consolida la versión oficial deduplicada mediante una clave unívoca basada en hash criptográfico SHA-256 (hash_duplicado).
  • Capa de Auditoría y Control (log_rechazos_calidad, rpt_limpieza_ejecucion, log_notificaciones): Almacena el histórico de excepciones por compuerta BPMN, las métricas de rendimiento y el log de alertas por correo.

3. Modelo Entidad-Relación Corregido

Con base en la retroalimentación de la fase preliminar, se perfeccionó el modelo conceptual eliminando el antipatrón de tabla desnormalizada (*God Table*) y articulando 13 entidades clasificadas en los 4 cuadrantes semánticos de DAMA-DMBOK v2:

Cuadrante DAMA Entidades del Modelo Responsabilidad en el Sistema
1. Reference Data cat_localidades, cat_barrios, cat_tipos_inmueble, cat_fuentes_origen Catálogos inmutables de Bogotá (DANE) y tipologías cerradas para evitar anomalías de inserción y modificación.
2. Pipeline & Ingesta wrk_datasets_ingesta, stg_inmuebles_raw, wrk_inmuebles_cleaned, fct_features_analiticas Almacenamiento transaccional de lotes ETL, aislamiento de datos crudos y feature store analítico.
3. Master Data (MDM) mdm_inmuebles_maestros, dim_entorno_urbano Registro maestro único consolidado (Golden Record) con deduplicación por hash SHA-256 y contexto de infraestructura urbana.
4. Calidad y Auditoría log_rechazos_calidad, rpt_limpieza_ejecucion, log_notificaciones Trazabilidad de registros descartados por compuerta BPMN, balance consolidado de ejecución ETL y alertas despachadas.
Cardinalidades Clave del Modelo:
• cat_localidades (1) ── (N) cat_barrios: Una localidad oficial de Bogotá contiene múltiples barrios georreferenciados.
• cat_barrios (1) ── (N) mdm_inmuebles_maestros: Un barrio ubica múltiples inmuebles maestros.
• stg_inmuebles_raw (1) ── (0..1) wrk_inmuebles_cleaned: Un registro crudo solo pasa a limpio si supera las compuertas de calidad.
• wrk_inmuebles_cleaned (1) ── (1) fct_features_analiticas: Relación biunívoca estricta para el vector de variables de Machine Learning.
• mdm_inmuebles_maestros (1) ── (1) dim_entorno_urbano: Todo inmueble maestro posee un perfil de amenidades y servicios.

5. Descripción del Sistema Gestor y de la Versión Utilizada

5.1 Motor SGBD: MySQL Server 8.0.x / 8.4 LTS

La implementación física se ejecutó sobre MySQL Server versión 8.0 / 8.4 LTS (compatible con la versión 26.7 LTS instalada en el laboratorio local y administrada mediante MySQL Workbench 8.0 CE). Se garantizó compatibilidad estándar con entornos equivalentes como MariaDB 10.4+ en XAMPP y phpMyAdmin.

5.2 Motor de Almacenamiento: InnoDB

Se configuró obligatoriamente ENGINE=InnoDB en las 13 tablas del esquema, garantizando:

  • Transaccionalidad ACID Plena: Soporte estricto de atomicidad y durabilidad mediante registros de bitácora transaccional (Write-Ahead Logging).
  • Integridad Referencial en Tiempo Real: Restricciones de clave foránea físicas con cláusulas de protección ON DELETE RESTRICT para catálogos y ON DELETE CASCADE para datos operacionales.
  • Exigencia Activa de Restricciones CHECK: A partir de MySQL 8.0.16, el motor InnoDB evalúa y rechaza cualquier operación DML que viole una restricción CHECK, devolviendo el código de excepción ERROR 3819 (HY000).

5.3 Juego de Caracteres y Cotejamiento: utf8mb4 / utf8mb4_unicode_ci

Para soportar adecuadamente el idioma español y la toponimia urbana de Bogotá D.C. (tildes en Usaquén, Engativá, diacríticos y la letra 'ñ' en Antonio Nariño), se estableció: 

CREATE DATABASE IF NOT EXISTS sistema_data_wrangling
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_unicode_ci;

El juego utf8mb4 asigna hasta 4 bytes por caracter Unicode, previniendo la corrupción de caracteres especiales que ocurría con el antiguo utf8 (3 bytes). El cotejamiento utf8mb4_unicode_ci proporciona comparaciones lingüísticas precisas e insensibles a mayúsculas/minúsculas.

9. Descripción de Errores Encontrados y Correcciones Aplicadas

Durante la fase de validación y contraste con las observaciones docentes de la entrega previa, se identificaron y solucionaron 5 aspectos críticos:

# Deficiencia Identificada Causa Raíz Solución Aplicada en instalacion.sql
1 Ausencia de validación de dominio en cat_fuentes_origen Se permitía ingresar cualquier texto en el formato del archivo o en el estado operativo de la fuente. Se implementaron dos restricciones CHECK:
• chk_fuente_formato: Dominios ('CSV','EXCEL','JSON','PARQUET','XML').
• chk_fuente_estado: Dominios ('ACTIVO','INACTIVO').
2 Estado de notificación sin restricción de catálogo La columna estado_envio en log_notificaciones admitía valores arbitrarios. Se añadió la restricción chk_notif_estado CHECK (estado_envio IN ('ENVIADO','FALLIDO','PENDIENTE')).
3 Bloqueo por claves foráneas al reejecutar scripts La ejecución de sentencias DROP TABLE en orden convencional fallaba con error 1217 / 1451 si existían dependencias activas. Se encapsuló la limpieza previa desactivando temporalmente la revisión de claves (SET FOREIGN_KEY_CHECKS = 0;), borrando en orden inverso (Grupo D a A) y reactivando la integridad de inmediato.
4 Inconsistencias espaciales por coordenadas desbordadas Existía riesgo de almacenar latitudes o longitudes fuera del polígono distrital de Bogotá D.C. Se integraron restricciones CHECK con el recuadro envolvente oficial:
• latitud BETWEEN 4.4500000 AND 4.8500000
• longitud BETWEEN -74.2500000 AND -73.9500000.
5 Interrupción de ejecución por pruebas negativas Las sentencias diseñadas para provocar error abortaban la ejecución secuencial completa del script en clientes batch. Se aislaron en la Sección 8 con comentarios descriptivos y documentación del error exacto retornado, permitiendo que el script principal corra de forma 100% continua.

10. Comparación Argumentada: Herramientas Gráficas vs. Sentencias SQL

El desarrollo de bases de datos relacionales en ingeniería de software plantea dos paradigmas metodológicos complementarios: el diseño mediante interfaces gráficas de usuario (GUI) y la codificación explícita de sentencias SQL. A continuación se fundamenta su comparación multidimensional:

Dimensión Modelado mediante Herramientas Gráficas (GUI)
(MySQL Workbench, ERwin, pgAdmin, DbSchema)		 Construcción mediante Sentencias SQL (CLI/Scripts)
(DDL, DML, Control de Versiones Git, CI/CD)
Usabilidad y Visualización Ventaja Principal: Permite diagramar esquemas complejos rápidamente mediante notación visual (Crow's Foot). Ideal para socializar conceptos con analistas y stakeholders. Limitada: El código SQL es abstracto para personas ajenas a la ingeniería. No permite apreciar la topología de relaciones a simple vista.
Control Fino del Motor Limitada: Los asistentes gráficos a menudo ocultan parámetros específicos del motor InnoDB, collation por columna, tamaños de buffer o restricciones CHECK avanzadas. Ventaja Absoluta: Control exacto de cada byte, tipo numérico, política ON DELETE, orden de índices B-Tree y comentarios de metadatos.
Integración en Git y Control de Versiones Deficiente: Guardan en formatos binarios propietarios (.mwb) o XMLs enormes donde mover una tabla un milímetro genera miles de líneas de conflicto en Git. Óptima: Archivos .sql en texto plano que producen *diffs* limpios, permitiendo revisiones de código (Pull Requests) y trazabilidad histórica precisa.
Automatización y CI/CD Inviable en servidores headless: No es posible abrir una interfaz gráfica en contenedores Docker de integración continua ni en servidores en la nube. Estándar de la Industria: Base del paradigma Infrastructure as Code (IaC). Permite despliegues automáticos desasistidos mediante pipelines.
Reproducibilidad Media: El código generado por *Forward Engineering* depende de la versión y configuración particular del software de modelado de cada máquina. Total y Determinística: Un script probado se ejecuta de manera idéntica en cualquier sistema operativo y servidor compatible.
Conclusión Metodológica:
En el marco de la ingeniería de software profesional, ambos enfoques se complementan: la GUI se utiliza en la fase de PLAN / Concepción para explorar el modelo conceptual y comunicar ideas, mientras que el Script SQL estandarizado e idempotente es el único artefacto válido y mandatorio para la fase de DEVELOPMENT / Operaciones y despliegue en producción.

11. Conclusiones sobre la Reproducibilidad del Script

  1. Idempotencia Demostrada: El diseño modular de instalacion.sql, articulado mediante sentencias condicionales IF NOT EXISTS, desactivación temporal de claves foráneas y orden topológico estricto, permite su ejecución indefinida sobre entornos limpios o preexistentes sin riesgo de estados intermedios inconsistentes.
  2. Portabilidad Multiplataforma: El script prescinde de rutas locales absolutas, sintaxis propietaria o extensiones de cliente. Es 100% interoperable entre MySQL Server 8.0, 8.4 LTS, MariaDB 10.4+, MySQL Workbench, phpMyAdmin y contenedores Docker en Linux.
  3. Cumplimiento de Estándares Internacionales: La implementación certifica el apego estricto a las normas ISO/IEC 9075:2016 (SQL), DAMA-DMBOK v2 (gobernanza y master data), ISO/IEC 25010 (índices y rendimiento) y las directrices de Clean Code e ingeniería de software del SWEBOK v4.
  4. Validación Ética y Segura: La inclusión de seed data 100% ficticia pero estructuralmente verosímil permite auditar todas las compuertas de negocio del mercado inmobiliario bogotano con total apego a la privacidad de datos.
